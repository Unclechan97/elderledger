# 03 技术选型

> 版本 v0.1 · 2026-09-11 · 前提：本地开发为基准，全链路零成本优先

## 0. 选型总览（最终结论）

| 层 | 选型 | 一句话理由 |
|----|------|-----------|
| 小程序端 | 微信原生小程序 + TypeScript | 插件兼容最稳、调试链路最短、无跨端需求 |
| 语音 ASR/TTS | 微信同声传译插件 WechatSI | 官方免费、ASR+TTS 一体、无需额外账号 |
| 文本语义解析 | GLM-4-Flash（json_schema 结构化输出） | 免费不限量、口语金额/日期/分类解析 |
| 图片识别 | GLM-4V-Flash（免费多模态） | 免费且比模板 OCR 更适配"支付截图" |
| 后端 | Node.js 20 + Express 5 + TypeScript | 轻、快、与前端同语言 |
| 数据库 | SQLite（better-sqlite3，WAL） | 零部署零运维，单文件易备份 |
| 开发调试 | 微信开发者工具 + 局域网真机预览 | 关闭域名校验，手机与电脑同 WiFi 即可 |

## 1. 小程序端：原生 vs Taro vs uni-app

| 维度 | 原生 | Taro | uni-app |
|------|------|------|---------|
| WechatSI 等插件兼容 | ★★★ 官方直连 | 需插件类型声明，偶有坑 | 可用但多一层封装 |
| 适老化自绘组件 | 直接写 | 需经 React 转译 | 需经 Vue 转译 |
| 包体积/启动 | 最小 | 略大 | 略大 |
| 调试 | 开发者工具直调 | 多一层编译 | 多一层编译 |
| 未来跨 App/H5 | 不支持 | 支持 | 支持 |

**结论：原生 + TypeScript。** 本项目无跨端需求，适老化 UI 本来就要大量自绘组件，原生链路最短、坑最少。跨端诉求记录为已知取舍：若未来要 App 端，届时评估 Taro 重写或仅做 H5 版。

UI 组件策略：**不引入 Vant/WeUI 大组件库**，只自绘 4 个核心组件（确认卡片、大键盘、分类九宫格、语音按钮）——适老化的字号与触控规范无法靠通用组件库达成。

## 2. 语音输入选型

| 方案 | 成本 | 准确率/方言 | 备注 |
|------|------|-------------|------|
| **A. WechatSI 插件** | 免费 | 普通话为主；TTS 支持普通话/粤语/四川话 | 微信智聆团队官方插件，ASR+TTS+翻译一体 |
| B. RecorderManager 录音 → 云端 ASR（腾讯云/讯飞） | 有免费额度，但需实名+计费账户 | 更强，方言包可选 | 引入账号与密钥管理成本 |
| C. 本地 funasr/whisper（Docker） | 免费 | 可选方言模型 | 真机需局域网上传音频，CPU 推理慢，MVP 不值得 |

**结论：A 为主。** 服务端预留 `/api/asr` 桩接口，若后续方言识别不达标再切 B/C，前端只换数据源。

### 已知细节与坑（开发时注意）

- 插件 APPID `wx069ba97219f66d99`，需在小程序管理后台「设置 → 第三方设置 → 插件管理」添加，`app.json` 声明 `provider`。
- `manager.start({ lang: 'zh_CN', duration: 30000 })`；纯英文输入时结果在 `onRecognize` 而非 `onStop`（本产品以中文为主，仍做空结果兜底）。
- TTS `textToSpeech` 文本 **≤ 150 字符**，返回临时音频地址（24h 失效）需用 `InnerAudioContext` 播放；多次点击需防抖。
- **开发者工具对麦克风/录音支持不完整，语音功能一律以真机验证为准。**

## 3. 图片识别选型

| 方案 | 成本 | 适配度 |
|------|------|--------|
| A. 微信服务市场 OCR 插件 | 按次收费 | 小票模板可用，支付截图支持差 |
| B. 腾讯云票据 OCR | 1000 次/月免费 | 票据强，但"支付截图"非标准票据，字段提取弱 |
| **C. 多模态 LLM：GLM-4V-Flash** | **完全免费**（单图 ≤ 5MB） | 小票+支付截图通吃，prompt 直接约定输出 JSON（金额/商户/日期/分类/置信度） |

**结论：C。** 老年人最高频的拍照对象是**微信/支付宝支付截图**（不是标准票据），模板类 OCR 覆盖差；多模态 LLM 天然处理非结构化版面，且与文本解析共用同一套智谱 API Key，运维成本最低。备选 B 留作图片量大/免费额度变化时的降级。

工程细节：`wx.chooseMedia` 用 compressed + `wx.compressImage` 控制在 5MB 内；识别后默认删除原图（隐私要求）。

## 4. 语义解析（语音文本 → 结构化记录）

- **GLM-4-Flash**：2024-08 起免费不限量；支持 `response_format: json_schema` 强制结构化输出；128K 上下文；约 72 tokens/s，延迟可接受。
- **正则兜底层**：服务端先跑一层轻规则（"数字+块/元"、日期词"昨天/早上"、分类关键词），规则命中且无歧义则不调 LLM —— LLM 挂了核心记账仍可用，且省延迟。
- 每次解析输出 `confidence`（0~1），< 0.7 前端自动转"预填手动页"。
- 用户已有智谱 open.bigmodel.cn 的使用基础（现有 API 体系一致），Key 管理与调用经验可直接复用。

## 5. 后端选型

| 候选 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **Express 5 + TS** | 极轻、中间件生态成熟、上手 10 分钟 | 大项目结构松散（本项目规模不会到大项目） | ✅ 选用 |
| NestJS | 结构化、依赖注入 | 起步重、样板代码多 | 杀鸡用牛刀 |
| Python FastAPI | 若未来自托管 ASR（Python 生态）更顺 | 当前无此需求；两语言并存的维护成本 | 不选，预留切换理由记录在案 |

**数据库：SQLite（better-sqlite3）** —— 同步 API 简单可靠、WAL 模式并发够用、单文件备份 = 拷贝文件。DAO 层隔离 SQL，未来换 MySQL 只动一层。
**不选微信云开发**：绑定微信生态、调试黑盒、本地开发体验差，与"本地为基准"矛盾。

**鉴权**：`wx.login` → `code2Session` 拿 openid 静默建用户；本地阶段不做手机号/密码体系；P1 家人绑定用"老人端生成 6 位邀请码 + 子女端输入"方案。

## 6. 本地开发与调试部署

```
微信开发者工具 ──http──> http://192.168.x.x:3000（本机 Express）
                              │
                              ├── SQLite 文件 server/data/elderledger.db
                              └── https──> open.bigmodel.cn（GLM-4-Flash / GLM-4V-Flash）
```

- 开发者工具勾选「不校验合法域名」；真机预览要求手机与电脑同一 WiFi，服务监听 `0.0.0.0`。
- GLM API Key 放 `server/.env`（已 gitignore），绝不入库、绝不写进小程序端代码。
- 上线期再评估：微信云托管（免运维、免域名备案）或轻量服务器 + 备案域名。

## 8. 技术风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| WechatSI 在开发者工具不可用/不稳定 | 开发效率 | 语音功能真机验证为主；mock 一层 voice service 便于 UI 开发 |
| GLM-4V 识别错金额 | 记错账 | 确认卡片强制二次确认；parse_log 留存；置信度阈值兜底 |
| 免费 API 限流/政策变化 | 解析不可用 | 正则兜底层保证"能记上"；服务端可配置切换模型名 |
| 方言/口音 ASR 误识别 | 语音不可用 | 引导普通话 + 识别文本大字可见可改 + 手动兜底 |
| 小程序类目审核 | 无法上线 | 个人主体注册时确认"记账"所需类目（如 工具 > 效率/信息查询），登记为上线前待办 |
| 图片超 5MB | 上传失败 | 前端压缩 + 服务端再校验，明确提示重拍 |
