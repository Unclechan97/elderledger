# 01 竞品与开源项目调研

> 调研时间：2026-09-11。目标：看清楚"老年人记账"这件事别人做到哪一步，确定本项目的借鉴点与差异定位。

## 一、结论（TL;DR）

| 维度 | 结论 |
|------|------|
| 现有产品最大缺口 | 没有一款产品同时做到「语音优先 + 拍照识别 + 适老大字 + 家人协同」 |
| 官方微信记账本 | 已覆盖"微信支付自动记账"，但现金、支付宝、人情往来靠手动，且无语音/拍照、非适老界面 |
| 开源项目 | 后端数据模型与账单导入值得借鉴（尤其 ezbookkeeping）；小程序开源记账多为练手项目，不建议直接二开 |
| 本项目机会点 | 老年人"不会打字、记不住、看不清"三痛 → 语音说一句/拍张照即记账 + 大字播报 + 子女远程可见 |

## 二、商业产品分析

| 产品 | 亮点 | 对老年人的问题 | 我们借鉴什么 |
|------|------|----------------|--------------|
| 随手记 | 账户/分类/报表体系最全，多账本 | 概念多（账户、项目、成员），上手门槛高 | 成熟的分类体系作为我们精简分类的参照 |
| 钱迹 | 无广告、无社交、本地优先、支持账单导入 | 仍以手动输入为主，键盘输入对老人不友好 | "两步记账"的交互克制度；CSV 导入/导出格式 |
| 鲨鱼记账 | 首页即记账、引导极简、图表好看 | 字号偏小，分类图标密集 | "打开第一屏就是记账"的信息架构 |
| **微信记账本（官方）** | **自动同步微信支付账单**，含消费/转账/红包，云端同步 | 仅覆盖微信支付；现金支出（老人占比高）缺失；界面非适老化；无语音/拍照 | 验证了"免安装、免注册、微信内闭环"是老年用户可接受的形态；确认卡片+自动分类思路 |
| 支付宝账单/预算 | 自动记录支付宝消费 | 同上，且老人支付宝使用率低于微信 | — |

**关键洞察**：老年人的支付结构是「现金 + 微信支付」为主，且高频支出是买菜、药品、人情往来（红包/礼金）——这三类恰好是微信记账本覆盖最弱的部分（现金完全缺失，人情往来语义复杂）。这就是本项目的切入点。

## 三、开源项目分析

### 3.1 自托管记账系统（后端/数据模型参考）

| 项目 | 技术栈 | 特点 | 可借鉴 | 不直接采用的原因 |
|------|--------|------|--------|------------------|
| [ezbookkeeping](https://github.com/mayswind/ezbookkeeping) | Go + Vue，单 Docker 容器 | 轻量、移动端友好、**中文友好**、支持导入微信/支付宝账单 CSV、多币种 | 账户-交易-分类的数据模型；微信/支付宝账单 CSV 的导入格式定义 | 无小程序端、无语音/图片识别、非适老化设计 |
| [Firefly III](https://github.com/firefly-iii/firefly-iii) | PHP (Laravel) + Vue | 功能最全：预算、规则引擎、循环交易、数据导入器（CSV/银行对接） | 规则引擎思路（对重复交易自动分类） | 太重（需数据库+PHP 环境），界面复杂，学习曲线陡 |
| [Actual Budget](https://github.com/actualbudget/actual) | Node.js + React | **本地优先（local-first）+ 端到端同步**，YNAB 信封预算法 | local-first 架构思想；同步模型 | 多币种弱、欧美使用习惯、预算法对老人过重 |
| GnuCash / Beancount / hledger | 桌面 / 纯文本 | 复式记账、数据严谨 | 导出格式兼容考虑（Beancount 纯文本） | 复式记账概念完全不适合目标用户 |

### 3.2 微信小程序方向的开源项目

- GitHub 上"微信小程序记账"项目数量多但**质量参差**：多为练手/毕设，典型栈为原生小程序或 uni-app + 微信云开发（云函数+云数据库），普遍缺少持续维护。
- [justjavac/awesome-wechat-weapp](https://github.com/justjavac/awesome-wechat-weapp) 是最全的小程序开源合集，可按需检索 UI 组件与工具库。
- **结论**：参考其 UI 布局与云开发数据模型，不直接二开；且本项目用本地 Node 服务而非云开发（便于本地开发、调试透明、可迁 self-host）。

### 3.3 值得抄的细节清单

1. **分类数据模型**：分类表与交易分离（category / transaction 两表），支持预置 + 自定义 —— ezbookkeeping 与 Firefly III 一致。
2. **金额存整数分**：避免浮点误差（各开源项目通用做法）。
3. **微信/支付宝账单 CSV 格式**：ezbookkeeping 的导入实现是现成的格式文档，P1 导出功能直接对齐，子女可帮老人把历史账单导入。
4. **"确认式自动分类"**：微信记账本自动分类后仍可修改 —— 我们的三种输入全部落到同一个"大卡片确认"上。
5. **local-first 思想**：Actual 证明本地优先 + 异步同步可行；我们本地开发阶段即单机 SQLite，P2 可加同步。

## 四、老年用户场景的特殊约束（调研补充）

| 约束 | 事实 | 对设计的影响 |
|------|------|--------------|
| 方言与口音 | 微信同声传译 ASR 以普通话为主，TTS 支持普通话/粤语/四川话 | 语音识别结果必须过 LLM 纠错（口语金额"十五块"、"两百"），且永远给手动兜底入口 |
| 视力 | 老花普遍，小字不可读 | 核心文本 ≥ 36rpx，金额 ≥ 72rpx，全局字号可调（详见需求文档） |
| 打字能力 | 拼音输入对多数 65+ 用户困难 | 一切输入以"说"和"按"优先，文本输入降到最低（备注可不填） |
| 信任与安全 | 老人是转账诈骗高危人群 | 家人协同（子女可见）是隐性刚需，也是卖点 |
| 记账中断成本 | 任何一步卡住就会放弃 | 说错可"重说"，识别错可点卡片改，全程 ≤ 3 步 |

## 五、差异定位一句话

> 微信记账本回答"微信支付自动记好了"；**银龄记账回答"剩下的现金、买菜、药费、人情，开口说一句/拍张照就记上，孩子也能帮着看"**。
